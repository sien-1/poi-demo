# POI 后端 MVP

这是一个独立运行的纯后端参考实现，用于验证数据分类、单位权限、分页检索、必要字段返回、患者任务和随访批次处理。它不依赖前端，也不读取或写入前端 `localStorage`。

> 当前实现使用内存中的合成数据。服务重启后所有修改消失，因此只能用于接口演示、技术验证和申报材料展示，不能承载真实患者数据。

## 技术选择

当前机器没有 Python、Node.js、.NET SDK 或 SQLite，因此 MVP 使用 Windows PowerShell 5.1 自带能力实现：

```text
PowerShell HTTP + JSON 合成数据
        ↓ 同一接口契约
PostgreSQL + 单体应用 + 对象存储
```

PowerShell 只是当前演示运行时，不是正式医疗后端。正式版建议继续使用单体架构，至少将存储替换为 PostgreSQL，并将演示令牌替换为微信登录或院内统一身份认证。

## 启动

在仓库根目录执行：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\backend\start.ps1
```

服务只监听本机回环地址：

```text
http://127.0.0.1:8765
```

健康检查：

```powershell
Invoke-RestMethod http://127.0.0.1:8765/health
```

查询演示患者：

```powershell
$headers = @{ "X-Demo-Token" = "doctor-c001" }
Invoke-RestMethod -Headers $headers `
  "http://127.0.0.1:8765/api/v1/patients?page=1&pageSize=5"
```

## 演示身份

请求头 `X-Demo-Token` 只用于本次合成数据演示。客户端不能通过 URL 或请求体自行声明角色、医院、科室和患者身份。

| 令牌 | 角色 | 数据范围 |
|---|---|---|
| `doctor-c001` | 医生 | 与 C001 存在有效诊疗关系的患者 |
| `doctor-c002` | 医生 | 与 C002 存在有效诊疗关系的患者 |
| `doctor-c003` | 医生 | 另一家演示医院的 C003 患者 |
| `doctor-c004` | 医生 | 与 C004 存在有效诊疗关系的患者 |
| `dept-admin-endo` | 科室管理员 | 本院妇科内分泌科 |
| `dept-admin-repro` | 科室管理员 | 本院生殖医学科 |
| `hospital-admin-h1` | 医院管理员 | 演示医院 H1 |
| `hospital-admin-h2` | 医院管理员 | 演示医院 H2 |

| `researcher-demo` | 研究人员 | 去标识化患者摘要 |

## 核心规则

- 患者主索引不直接固定医院、科室或医生。
- 当前归属由有效的 `careRelationships` 记录决定。
- 转诊时结束旧关系并新增关系，不覆盖历史记录。
- 任务保留下发时的医院、科室和医生上下文。
- 医生只能访问与自己存在有效诊疗关系的患者。
- 科室管理员按科室过滤，医院管理员按医院过滤。
- 患者只能读取本人任务和问卷。
- 列表不返回姓名、电话、身份证号等直接身份信息。
- 医生查看问卷时默认只返回摘要，不返回原始答案。
- 无权确认对象是否存在时统一返回 `404`，不通过不同错误提示泄露患者存在性。
- 列表统一使用 `page`、`pageSize` 和 `meta.total`，排序结果稳定。
- 重复完成任务安全返回已完成结果；问卷重复提交返回 `409`。
- 任务生成批次使用 `idempotencyKey`，重复请求不重复创建任务。
- 一个任务批次只能处理同一医院、科室和医生的访视。
- 关键查看、提交和批次操作写入只增不改的审计日志。

## 合成数据覆盖

种子文件为 `data/demo-seed.json`，包含：

- 2 家演示医院、3 个科室、4 位医生、10 位虚拟患者。
- 30 个随访访视。
- 跨科室转诊患者和跨医院历史关系患者。
- 完整、待访、逾期和缺失场景。
- 4 组问卷实例，覆盖已提交、待提交和重复提交保护。
- 医生、科室管理员、医院管理员、患者和研究人员身份。

种子中不包含真实姓名、电话、身份证号、病案号或真实就诊信息。

## 验收

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\backend\test-api.ps1
```

测试会启动临时服务并验证：

- 健康检查、鉴权和错误结构。
- 患者目录分页、搜索和敏感字段裁剪。
- 医生、科室、医院和患者四层越权隔离。
- 病史与任务中的单位上下文保留。
- 任务完成幂等性和问卷只写一次。
- 批次任务生成幂等性和跨单位拒绝。
- 审计事件和研究人员去标识化返回。

当前验收基线为 **22 项通过**。

## 接口与目录

- 接口说明见 `API.md`。
- 服务入口为 `server.ps1`。
- HTTP、鉴权、权限、资源、批次和路由分别位于 `lib/`。
- 数据仅存在于服务进程内，不设置共享状态文件。

## 正式化前必须完成的改造

1. 将合成数据存储替换为 PostgreSQL，并建立外键、唯一约束、事务和迁移。
2. 接入微信登录或院内统一身份认证，不在客户端传角色和单位。
3. 将演示令牌替换为短期会话、权限校验和令牌撤销机制。
4. 将内存数组更新改为事务化仓储层，避免并发覆盖。
5. 引入 `study`、研究中心和入组关系，完成研究项目级隔离。
6. 原始答案、计分结果和量表版本改为不可覆盖的受控记录。
7. 增加知情同意、文件对象存储、数据导出审批和下载水印。
8. 完成 HTTPS、访问日志、备份恢复演练、伦理和安全审批。
9. 接入真实数据前，删除或禁用全部 `X-Demo-Token` 身份。

## 不应据此架构推断的内容

- 本实现没有完成真实登录、加密、数据库事务、备份或高可用。
- 本实现没有接入真实患者、真实医嘱、真实 OCR 或真实量表计分。
- 本实现不是医疗诊断、处方或治疗建议系统。
- Excel 仅可作为业务沟通示例，不是本后端的数据源或正式存储方案。
